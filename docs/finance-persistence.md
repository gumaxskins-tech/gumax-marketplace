# Finance persistence

Completed: ledger, hold, order, payment and refund idempotency extraction, plus payment event/webhook deduplication, each behind an explicit in-memory adapter for tests. P0-A1.1a is complete: all six idempotency/deduplication mechanisms are decoupled from FinanceService. LedgerRepository, WalletRepository, HoldRepository, OrderRepository, PaymentRepository, RefundRepository and InventoryReservationRepository are also extracted and currently use in-memory adapters; they are not PostgreSQL persistence. Wallet balance remains derived from the ledger. P0-A1.1b is complete only in the sense that main finance and inventory-reservation storage is behind repository ports. FinanceTransactionContext and InMemoryFinanceTransactionManager now provide an async composition boundary with one shared set of finance dependencies. The six idempotency/dedup ports and all seven main repository ports, including their in-memory adapters, are asynchronous. FinanceService awaits every affected store and repository call, including its separate item-only `reserve()` operation. P0-A1.1d async propagation is complete. Wallet still has no authoritative balance field.

Pending: persistent idempotency adapters with database scope/key semantics; PrismaTransactionManager; Prisma adapters; PostgreSQL transactions; row-level locking or conditional reservation; atomic order/reservation, payment/order/event-dedup/audit and hold/ledger-capture flows; Audit persistence; and persistent wallet/ledger/payment/refund state. InMemoryFinanceTransactionManager is a composition boundary only: it shares context and propagates errors but provides no rollback or production atomicity. HoldRepository being async does not make capture atomic: its hold transition and ledger append still lack one production transaction. The separate item-only `reserve()` operation is not coupled to `createOrder()` and has no owner/order linkage or FinanceService release flow; it must not be represented as a production order-reservation workflow unchanged. PaymentRepository being async does not make webhook payment/order/event-dedup/audit atomic. RefundRepository being async does not add ledger or settlement behavior: refunds retain their current in-memory record-only semantics, and refund/payment/audit are not a PostgreSQL transaction. InMemoryInventoryReservationRepository is a composition/test double: exclusivity works only for a shared adapter in one process and is not a distributed or crash-safe guarantee. P0-A1 is not complete.
