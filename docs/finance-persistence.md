# Finance persistence

Completed: ledger, hold, order, payment and refund idempotency extraction, plus payment event/webhook deduplication, each behind an explicit in-memory adapter for tests. P0-A1.1a is complete: all six idempotency/deduplication mechanisms are decoupled from FinanceService. LedgerRepository, WalletRepository, HoldRepository, OrderRepository, PaymentRepository, RefundRepository and InventoryReservationRepository are also extracted and currently use in-memory adapters; they are not PostgreSQL persistence. Wallet balance remains derived from the ledger. P0-A1.1b is complete only in the sense that main finance and inventory-reservation storage is behind repository ports. FinanceTransactionContext and InMemoryFinanceTransactionManager now provide an async composition boundary with one shared set of finance dependencies. The six idempotency/dedup ports and all seven main repository ports, including their in-memory adapters, are asynchronous. FinanceService awaits every affected store and repository call, including its separate item-only `reserve()` operation. P0-A1.1d async propagation is complete. P0-A1.2b routes `createOrder()` through the generic transaction manager: `OrderIdempotencyStore`, `InventoryReservationRepository`, and `OrderRepository` use the callback context. An `OrderItem` with `source: "INVENTORY"` must name its actual `inventoryItemId`, which is reserved exclusively; `source: "ORDER"` represents encomenda and does not create an inventory reservation. P0-A1.2c routes verified webhooks through the generic transaction manager: `PaymentEventDedupStore`, `PaymentRepository`, and `OrderRepository` use the callback context. P0-A1.2d routes refunds through the generic manager: `RefundIdempotencyStore`, `PaymentRepository`, and `RefundRepository` use the callback context. P0-A1.2 is complete as an in-memory transaction-composition phase. Wallet still has no authoritative balance field. P0-A1.3c adds `PrismaWalletRepository`, and P0-A1.3d adds append-only `PrismaLedgerRepository`; both accept the client surfaces shared by `PrismaClient` and `Prisma.TransactionClient`, are structurally tested only, and are not yet PostgreSQL integration-tested. P0-A1.3h migrates Ledger idempotency to the approved `claim`/`complete` runtime contract and in-memory lifecycle adapter. P0-A1.3i adds `PrismaLedgerIdempotencyStore`, also transaction-client-compatible, using the approved race-safe `createMany({ skipDuplicates: true })` claim protocol and typed Ledger result relation; PostgreSQL migration execution and concurrency integration testing remain pending. P0-A1.3j prepares the Hold database prerequisites: the explicit `CAPTURED` lifecycle value and `WalletHold(walletId, status)` index required by `listActiveByWallet`. P0-A1.3k adds `PrismaHoldRepository`, with a transaction-client-compatible `walletHold` delegate, lossless domain conversion, and no Wallet balance behavior. P0-A1.3l adds `createPrismaCaptureTransactionResources(client)`, which constructs the Hold, Ledger, and Ledger idempotency adapters with exactly one supplied transaction-scoped client. P0-A1.3m adds the matching narrow payments contract: `CaptureTransactionContext`, `CaptureTransactionManager`, and `InMemoryCaptureTransactionManager`; `capture()` now uses only that boundary while the full `FinanceTransactionManager` remains responsible for createOrder/webhook/refund. P0-A1.3n adds `PrismaCaptureTransactionManager`: its injected host executes one `$transaction` per `run()`, and the callback receives the resource bundle constructed from that exact transaction client. It is available for future injection but is not yet wired into a running FinanceService.

Pending: PrismaFinanceTransactionManager; PostgreSQL migration execution and integration testing for the Prisma Ledger and Hold adapters; injection of `PrismaCaptureTransactionManager` into the running FinanceService; other idempotency adapters with database scope/key semantics; remaining Prisma adapters; row-level locking or conditional reservation; atomic order/reservation, payment/order/event-dedup/audit and hold/ledger-capture flows; Audit persistence; and persistent wallet/ledger/payment/refund state. `PrismaCaptureTransactionManager` calls its injected host's `$transaction(async tx => ...)` and composes capture resources from that same `tx`, but its unit fakes prove lifecycle and composition only—not PostgreSQL rollback, isolation, concurrency, or atomicity. Ledger idempotency DB prerequisites are prepared: a typed `ledgerEntryId` FK, same-transaction claim/append/complete lifecycle triggers, and immutable completed results are defined in [ledger-idempotency-persistence-design.md](ledger-idempotency-persistence-design.md). `credit()` and `debit()` still require production transaction-scoping before persistent claim/append can be atomic. InMemoryFinanceTransactionManager and InMemoryCaptureTransactionManager are composition boundaries only: they share context and propagate errors but provide no rollback or production atomicity. Routing `capture()` through the narrow manager does not make capture atomic: a hold transition can still remain after a later ledger failure. Likewise, if an in-memory inventory reservation succeeds and the subsequent order save fails, the reservation can remain without an Order; no compensation is performed. Routing the webhook through the manager does not make event deduplication, payment, and order updates atomic; an in-memory failure after the event record can leave partial state. Webhook audit remains the service's in-memory collection outside the transaction context, so it is not transaction-scoped or persistent. Routing refunds through the manager does not make refund persistence atomic; an in-memory failure after the refund save and before idempotency completion can leave partial state. Refund audit also remains outside the transaction context. Refunds still have no ledger or provider settlement effect. InMemoryInventoryReservationRepository is a composition/test double: exclusivity works only for a shared adapter in one process and is not a distributed or crash-safe guarantee. P0-A1 is not complete.

## P0-A1.3o PostgreSQL environment gate

On 2026-09-07, the first real-PostgreSQL validation was blocked before any connection: `GUMAX_TEST_DATABASE_URL`, `TEST_DATABASE_URL`, and `DATABASE_URL` were unset; no local PostgreSQL, `psql`, `pg_isready`, Docker, local Prisma CLI, or generated `@prisma/client` was available. No migration, schema change, or database reset was attempted. The next safe run requires a clearly disposable `GUMAX_TEST_DATABASE_URL` (with its host, port, and database name reviewed before use), workspace-installed Prisma 6.2.1 and generated client, and a disposable PostgreSQL service. It must validate with the local Prisma binary and apply the complete migration chain before adding/running the dedicated capture transaction PostgreSQL smoke test. This gate does not validate rollback, same-key concurrency, or capture atomicity.

The reproducible npm, Prisma, test-URL, migration, and cleanup contract is documented in [postgres-integration-testing.md](postgres-integration-testing.md). The external environment used npm `11.17.0` with Node `24.19.0`, while the manifest intentionally remains `npm@10.9.2`. A first disposable-PostgreSQL `migrate deploy` attempt safely exposed that the prior migration chain had no empty-database baseline: the first incremental referenced a missing `IdempotencyRecord` (`42P01`). `20260905000000_initial_baseline` now represents the historical schema immediately before the ledger-idempotency incremental, so the full chain can bootstrap an empty database. Fresh-database migration-chain revalidation, real transaction smoke, rollback, and concurrency tests remain pending.

P0-A1.3o capture PostgreSQL smoke is defined in `packages/database/test/postgres-capture.integration.test.ts`. It requires `GUMAX_TEST_DATABASE_URL` explicitly and uses a real Prisma client only in its test harness. The commit and deliberate post-write rollback probes have passed on the VPS.
