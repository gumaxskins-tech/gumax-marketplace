# Finance persistence

Completed: ledger, hold, order, payment and refund idempotency extraction, plus payment event/webhook deduplication, each behind an explicit in-memory adapter for tests. P0-A1.1a is complete: all six idempotency/deduplication mechanisms are decoupled from FinanceService. LedgerRepository, WalletRepository, HoldRepository, OrderRepository, PaymentRepository, RefundRepository and InventoryReservationRepository are also extracted and currently use in-memory adapters; they are not PostgreSQL persistence. Wallet balance remains derived from the ledger. P0-A1.1b is complete only in the sense that main finance and inventory-reservation storage is behind repository ports. FinanceTransactionContext and InMemoryFinanceTransactionManager now provide an async composition boundary with one shared set of finance dependencies. The six idempotency/dedup ports and all seven main repository ports, including their in-memory adapters, are asynchronous. FinanceService awaits every affected store and repository call, including its separate item-only `reserve()` operation. P0-A1.1d async propagation is complete. P0-A1.2a routes `capture()` through FinanceTransactionManager: hold mutation, ledger append, and ledger idempotency use the transaction callback context. P0-A1.2b routes `createOrder()` through the transaction manager: `OrderIdempotencyStore`, `InventoryReservationRepository`, and `OrderRepository` use the callback context. An `OrderItem` with `source: "INVENTORY"` must name its actual `inventoryItemId`, which is reserved exclusively; `source: "ORDER"` represents encomenda and does not create an inventory reservation. P0-A1.2c routes verified webhooks through the transaction manager: `PaymentEventDedupStore`, `PaymentRepository`, and `OrderRepository` use the callback context. Wallet still has no authoritative balance field.

Pending: persistent idempotency adapters with database scope/key semantics; PrismaTransactionManager; Prisma adapters; PostgreSQL transactions; row-level locking or conditional reservation; atomic order/reservation, payment/order/event-dedup/audit and hold/ledger-capture flows; Audit persistence; and persistent wallet/ledger/payment/refund state. InMemoryFinanceTransactionManager is a composition boundary only: it shares context and propagates errors but provides no rollback or production atomicity. Routing `capture()` through it does not make capture atomic: a hold transition can still remain after a later ledger failure. Likewise, if an in-memory inventory reservation succeeds and the subsequent order save fails, the reservation can remain without an Order; no compensation is performed. Routing the webhook through the manager does not make event deduplication, payment, and order updates atomic; an in-memory failure after the event record can leave partial state. Webhook audit remains the service's in-memory collection outside the transaction context, so it is not transaction-scoped or persistent. RefundRepository being async does not add ledger or settlement behavior: refunds retain their current in-memory record-only semantics, and refund/payment/audit are not a PostgreSQL transaction. InMemoryInventoryReservationRepository is a composition/test double: exclusivity works only for a shared adapter in one process and is not a distributed or crash-safe guarantee. P0-A1 is not complete.
